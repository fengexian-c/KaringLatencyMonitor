# Karing 延迟监控使用指南

Karing 延迟监控是一个独立的轻量 Windows 客户端。它通过 Karing 本地 Clash API 定时探测指定节点，把延迟和可用率时间序列保存在本机 SQLite 中，并按最近 24 小时、7 天和 30 天显示统计结果。

## 1. 运行要求与版本选择

- Windows 10 1809 或更高版本。
- Karing 已安装并正在运行。
- Karing 已启用 Clash API / External Controller。

发布包有两个版本：

| 发布包 | 适用场景 |
|---|---|
| `KaringLatencyMonitor-win-x64.zip` | 推荐。包含 Windows App Runtime，无需另装 .NET 或 Windows App Runtime。 |
| `KaringLatencyMonitor-win-x64-lean.zip` | 体积更小，无需 .NET，但电脑必须已经安装 Windows App Runtime 2.0。 |

如果不确定应选择哪个版本，请使用推荐的 `KaringLatencyMonitor-win-x64.zip`。

## 2. 安装与启动

1. 完整解压 ZIP，不要直接在压缩包内运行。
2. 将应用目录放在当前用户可写的位置，例如文档目录或其他数据盘目录。不要放入通常需要管理员权限写入的 `Program Files`。
3. 先启动 Karing。
4. 运行 `KaringLatencyMonitor.App.exe`。

应用关闭窗口后会继续留在系统托盘；需要完全结束时，请在托盘菜单中选择“退出”。

## 3. 首次连接 Karing

展开左侧的“连接与采集设置”，填写以下内容：

| 设置 | 默认值 | 说明 |
|---|---|---|
| 控制器地址 | `http://127.0.0.1:3057` | Karing Clash API / External Controller 的监听地址。 |
| API secret | 空 | 在 Karing 中依次打开“设置 → 在线面板”，从在线面板链接的 `secret=xxxxx#/proxies` 中提取 `xxxxx`。 |
| 探测目标 URL | `https://www.gstatic.com/generate_204` | Karing 将通过被测节点访问的目标，可按需要更换。 |
| 超时 | 15 秒 | 单个节点一次探测允许等待的最长时间。 |
| 并发 | 5 | 同时探测的节点数量。 |
| 周期 | 10 分钟 | 自动采集间隔。 |
| 自动采集 | 开启 | 开启后按照周期持续采集。 |

填写完成后：

1. 点击“保存设置”。
2. 点击窗口顶部的“刷新分组”。
3. 状态栏显示“已连接 Karing”后，从节点组下拉列表中选择需要监控的组。

API Secret 保存在 Windows Credential Locker，不会写入 SQLite 或 `settings.json`。

## 4. 选择节点与开始采集

选择节点组后，左侧会显示该组当前存在的节点：

- 勾选需要参与采集和统计的节点。
- 使用“全选”“清空”“反选”批量修改选择。
- 使用“搜索节点”过滤较长的节点列表。
- 点击“立即采集”可立即执行一轮探测。
- 开启“自动采集”后，程序会按设定周期持续探测，包括窗口隐藏到托盘时。

节点选择按组独立保存。左右两侧都不会显示已经移除的节点；左侧显示当前组的所有现有节点，右侧统计和采集范围只包含已勾选节点。`GLOBAL` 等合成组首次出现时默认不勾选节点，以免立即探测数百项。

如果同一个节点标签出现在多个组中，它的延迟和可用率历史会跨组共享，但各组的勾选状态仍相互独立。

## 5. 查看最近 24 小时

右侧每个选中节点固定占一行。最近 24 小时区域从左到右显示 24 个一小时时间格，越靠右越接近当前时间。

延迟色块含义：

| 颜色 | 含义 |
|---|---|
| 绿色 | `< 100 ms` |
| 浅绿 | `100–199 ms` |
| 黄色 | `200–299 ms` |
| 橙色 | `300–399 ms` |
| 红色 | `>= 400 ms` |
| 灰色 | 本小时有节点探测，但全部失败或超时 |
| 白色 | 没有节点采样，或者 Karing 控制器离线 |

一个小时内有多次成功采样时，色块按照成功样本的平均延迟着色。

每个色块下方的 5px 圆点表示同一小时的可用率：

- 绿色：`100%`
- 黄色：`50% <= 可用率 < 100%`
- 红色：`0% < 可用率 < 50%`
- 灰色：有探测但全部失败
- 不显示圆点：没有节点探测或控制器离线

## 6. 24 小时、7 天和 30 天统计

每个时间范围均显示两项数据：

```text
平均延迟 = 成功样本的延迟总和 / 成功样本数
可用率   = 成功节点探测数 / 节点探测总数 × 100%
```

Karing 控制器离线时不会生成节点失败样本，因此不会降低节点可用率。

- 显示“失败”：该时间范围有探测，但没有任何成功样本。
- 显示“—”：该时间范围完全没有节点探测数据。

## 7. 调整节点顺序和统计排序

- 左侧节点列表是默认顺序编辑区。清空搜索内容并等待刷新或采集结束后，可拖动节点调整当前组的默认顺序。
- 新节点会追加在自定义顺序之后；节点被移除后隐藏，重新出现时恢复原有位置和勾选状态。
- 点击右侧“节点”列名旁的按钮，可以恢复左侧定义的默认顺序。
- 点击 24 小时、7 天或 30 天下方“延迟”“可用率”旁的按钮，可以切换升序和降序。
- 统计排序设置按节点组保存。

## 8. 托盘运行

- 关闭主窗口只会把应用隐藏到系统托盘，不会停止自动采集。
- 从托盘可以重新打开窗口、立即采集或完全退出。
- 隐藏到托盘时，应用会释放不活跃的窗口内存；重新打开后内存按需恢复属于正常现象。
- 再次运行 EXE 会激活已经存在的实例，不会同时启动多个采集器。

## 9. 数据、备份与更新

SQLite、设置和日志统一保存在 EXE 同目录的 `data` 子目录：

```text
KaringLatencyMonitor.App.exe
data\
  latency.db
  settings.json
  startup.log
```

- `latency.db`：节点组、节点选择、采集批次、延迟和可用率历史。
- `settings.json`：控制器地址、探测参数和其他非敏感设置。
- `startup.log`：启动诊断信息。

应用每次启动时会删除 31 天之前的采样，以及已经没有样本引用的旧采集批次。

备份或迁移时，先从托盘完全退出应用，再复制整个 `data` 目录。升级程序时保留原有 `data` 目录并替换其他程序文件即可。发布 ZIP 不包含开发或打包机器上的运行数据。

## 10. 常见问题

### 如何正确获取 API secret

1. 打开 Karing。
2. 依次进入“设置 → 在线面板”。
3. 查看或复制在线面板链接。
4. 找到链接中的 `secret=xxxxx#/proxies`，其中 `xxxxx` 就是监控程序需要填写的 API Secret。

例如在线面板链接为：

```text
http://127.0.0.1:3057/ui/?secret=abc123#/proxies
```

应在监控程序的“API secret”中只填写：

```text
abc123
```

不要包含 `secret=`、`#/proxies`、引号或 `Bearer` 前缀。填写后点击“保存设置”，再点击“刷新分组”。

### Karing 有多个配置，但这里只显示少量节点组

这里显示的是当前运行配置实际生成的出站组，不是 Karing“配置排序”中的订阅或配置档案。`GLOBAL` 是 Clash 面板接口提供的合成组，也可能出现在列表中。

### 色块为什么是白色而不是灰色

灰色表示已经对该节点发起探测但失败；白色表示该小时没有节点采样，或者当时 Karing 控制器离线。控制器离线不会被误算为所有节点不可用。

### Lean 版本无法启动

确认系统已安装 Windows App Runtime 2.0，或者直接改用包含运行时的 `KaringLatencyMonitor-win-x64.zip`。

### 程序启动失败

查看 EXE 同目录 `data\startup.log` 中的诊断信息。
