# 实现说明

## 1. 总体结构

应用分为两个项目：

- `KaringLatencyMonitor.Core`：Karing HTTP API、采集调度核心、SQLite 存储与统计聚合，不依赖 UI。
- `KaringLatencyMonitor.App`：WinUI 3 原生窗口、节点组与节点选择、24 格热力图、托盘和设置持久化。

前端只消费 SQLite 聚合后的 `DashboardSnapshot`，不会把 API 响应直接当作历史数据。这样即使 Karing 重启，已经采集的历史仍然可查。

## 2. 节点组发现和采集流程

1. `GET /group/` 获取真正实现 `OutboundGroup` 的运行时出站组。
2. `GET /proxies` 获取 Clash 面板的代理字典，并补入其中带 `all` 成员列表但不在 `/group/` 中的合成组。Karing/sing-box 会在这里人为插入 `GLOBAL`。
3. 两个结果按名称合并；真实出站组保留原始定义，代理列表独有的合成组默认不勾选任何节点，避免选择 `GLOBAL` 后立即探测数百项。
4. 用户选择普通组后，请求 `GET /group/{Uri.EscapeDataString(groupName)}` 刷新；若该地址返回 404（例如合成 `GLOBAL`），回退到 `GET /proxies` 中的同名对象。
5. Karing“配置排序”中的订阅/配置档案不是运行时出站组，不会按档案数量出现在这里；只有当前运行配置实际生成的组可被探测。
6. 节点和组成员写入 `node_group`、`node`、`group_member`；被用户勾选的节点写入 `monitor_selection`。
7. 每轮采集先刷新当前组，再读取“已勾选且仍在组内”的节点。
8. 在并发上限内调用：

   ```text
   GET /proxies/{escaped-tag}/delay?url={escaped-target}&timeout={seconds}
   ```

9. 成功响应只读取正整数 `delay`。即使响应还带有 `delay2` 或其他字段，也不会存储或参与计算。
10. 一轮结果用同一个 SQLite 事务写入 `probe_run` 与 `latency_sample`。

API secret 通过 `Authorization: Bearer ...` 发送，保存在 Windows Credential Locker。

## 3. 失败和离线语义

- 节点请求返回非成功 HTTP、无有效 `delay`、JSON 无效或节点级超时：写一条 `ok=0`、`delay_ms=NULL` 的节点样本。这类样本进入可用率分母，并在小时内没有任何成功样本时显示灰色。
- 获取节点组时无法连接控制器，或一轮内所有探测都无法连接控制器：采集批次标为 `controller_offline`，不写节点失败样本。因此不会因为 Karing 本身离线而把所有节点判为不可用。
- 一个小时内既发生控制器离线又存在节点样本：色块仍按节点样本显示，悬停提示会注明该小时控制器曾离线。
- 未授权和其他控制器 API 错误记录为失败批次，不伪造成节点失败。

## 4. SQLite 数据模型

数据库固定为 EXE 同目录的 `data\latency.db`，普通构建和便携包使用相同规则。设置、启动日志和运行时托盘图标也统一写入这个 `data\`。因此应用应部署在当前用户可写目录，而不是 `Program Files`。数据库启用 WAL、外键、`synchronous=NORMAL` 和 5 秒 busy timeout。

| 表 | 作用 |
|---|---|
| `node_group` | 节点组类型、当前节点、最后发现时间 |
| `node` | 节点类型及首次/最后发现时间 |
| `group_member` | 组和节点的有序成员关系、当前是否仍存在 |
| `monitor_selection` | 每个组独立保存的节点勾选状态 |
| `group_node_order` | 每个组由用户拖动产生的默认节点顺序 |
| `group_sort_preference` | 每个组右侧统计表当前使用的排序字段与方向 |
| `probe_run` | 每轮采集的开始/结束、状态、预期数、成功数和失败数 |
| `latency_sample` | 每个节点的测量时间、`delay_ms`、成功标志、错误与请求耗时 |

`latency_sample` 的主键是 `(run_id, tag)`；索引 `(tag, measured_at_ms)` 支持按节点读取时间序列。样本以节点 `tag` 为主体全局共享，`run_id` 只记录样本来自哪一轮采集。同一个节点出现在多个组时，各组会复用它的历史延迟与可用率，不会复制数据。已有 SQLite 中的历史样本也直接适用，无需迁移。

`group_member` 和 `monitor_selection` 仍按组隔离，因此每个组可以独立决定是否显示和采集该节点。`probe_run` 中的控制器离线状态也仍然只影响发起该轮采集的组，不会扩散到其他组。应用启动时删除 31 天之前的样本和已经没有样本引用的旧批次。

刷新节点组时，已不在控制器响应中的成员只标记为 `is_present = 0`，不会删除历史。左右两侧界面都只查询 `is_present = 1` 的当前成员；定时或立即采集完成后会同步重载两侧，因此已移除节点立即隐藏。节点重新出现后会恢复原有勾选状态和共享历史。

## 5. 24 格和统计口径

仪表盘锚点向上对齐到最近的 5 分钟，最近 24 小时被切成 24 个固定的一小时区间，左旧右新。例如 14:47 加载时使用 14:50 作为锚点，使刚写入的 14:47 样本立即进入最右侧时间格。查询区间仍为左闭右开；最右侧格的结束时间最多比加载时刻晚不到 5 分钟，未来部分不会产生样本。

每小时色块：

- 有至少一个成功样本：使用成功样本的平均 `delay_ms` 着色；失败样本仍计入该小时的可用率。
- 有探测但全部失败：灰色。
- 没有节点探测，或者只有控制器离线批次：白色；悬停提示区分具体原因。

每个色块下方在行间净空中绘制一个直径 5px 的可用率圆点，与对应小时水平居中：

- `100%`：绿色。
- `50% <= 可用率 < 100%`：黄色。
- `0% < 可用率 < 50%`：红色。
- 有探测但全部失败：灰色。
- 没有节点探测或控制器离线：不绘制圆点。

圆点直接复用小时聚合的成功数和探测总数，不新增 SQLite 字段或查询。

阈值固定为：

| 区间 | 颜色 |
|---|---|
| `< 100 ms` | 绿色 |
| `100–199 ms` | 浅绿 |
| `200–299 ms` | 黄色 |
| `300–399 ms` | 橙色 |
| `>= 400 ms` | 红色 |

24 小时、7 天和 30 天三组统计使用相同口径：

```text
平均延迟 = SUM(成功样本 delay_ms) / 成功样本数
可用率   = 成功节点探测数 / 节点探测总数 * 100%
```

控制器离线批次没有节点样本，因而不进入可用率分母。没有成功样本但存在失败探测时，平均延迟显示“失败”；完全没有探测时显示“—”。

## 6. UI 和运行方式

- 左栏：节点组、节点筛选、全选/清空/反选、连接和采集设置。节点组选择器使用底部左对齐的 `DropDownButton + Flyout/ListView`，避免 WinUI `ComboBox` 默认浮层覆盖原选择框和分区标题。
- 左侧节点列表是唯一的默认顺序编辑器：搜索为空且当前未刷新/采集时允许拖动。顺序按组写入 `group_node_order`；Karing 新增节点追加在自定义顺序之后，移除节点隐藏，重新出现时恢复原位置。
- 右栏：每个选中节点固定一行，依次显示节点名、24 个色块，以及 24 小时/7 天/30 天的平均延迟和可用率。三个时间范围之间用细灰线分隔。“节点”按钮恢复左侧定义的默认顺序，各时间范围的“延迟”和“可用率”按钮分别切换升序/降序。按延迟排序时，探测失败和无数据始终排在有效延迟之后；按可用率排序时，有采样但全部失败按 `0%` 参与排序，无采样置后；数值相同时均以默认顺序稳定排序。
- 一行的 24 个色块和 24 个可用率圆点不创建独立的 `Border`/`Ellipse`；`HeatmapStrip` 把它们一起绘制到一个 237×21 的 `WriteableBitmap`。色块保持在 36px 行内的 Y=11–25，圆点占用其下方净空的 Y=27–32，整行只保留一个图像元素和一个按指针位置复用的 ToolTip。列表仍由 `ListView` 虚拟化。
- 自动采集用单一调度器串行触发；采集服务还有非阻塞互斥门，防止手动和定时任务重叠。
- 关闭窗口时隐藏到托盘；再次启动会激活现有实例。
- 进入托盘是低频、用户触发的边界：应用请求一次 LOH 压缩和完整 GC，再调用 `SetProcessWorkingSetSize(-1, -1)` 返还不活跃物理页；周期采集路径不会强制 GC。
- `startup.log` 记录 XAML、窗口和 ViewModel 启动阶段，便于定位目标机器上的运行时问题。

## 7. 发布与 AOT

- 推荐包使用 NativeAOT、裁剪、尺寸优先优化，不依赖目标机的 .NET 运行时。
- `portable` 同时携带 Windows App Runtime；`lean` 依赖目标机已安装的 Windows App Runtime 2.0。
- 设置 JSON 使用 `System.Text.Json` 源生成上下文，XAML 可绑定类型使用 C#/WinRT 2.3.1 的 `GeneratedBindableCustomProperty` 源生成，避免 AOT 下反射和集合 `ItemsSource` 封送失败。
- Windows App SDK 2.0.1 对未打包 NativeAOT 发布不会自动复制应用自有 PRI/XBF。项目的发布目标会递归复制 XBF、保留子目录，并复制 PRI；打包脚本还会校验 `Controls\HeatmapStrip.xbf`。
- 发布脚本先写入临时目录和 ZIP；更新可直接运行副本时会保留已有 `data\`，且不会把该目录写进 ZIP。

## 8. 验证覆盖

`test.ps1` 当前覆盖：

- 五档延迟颜色的全部边界值。
- 可用率圆点四档颜色及无数据状态的全部边界值。
- 仪表盘锚点在整 5 分钟、边界后 1ms 和下个边界前 1ms 的向上对齐行为。
- `GET /group/`、转义后的组/节点路径、Bearer 认证，以及只采用 `delay`、忽略 `delay2`。
- SQLite 24 小时平均延迟和可用率、节点失败、无数据、控制器离线不进入分母。
- 每个节点组独立保存选择状态。

此外，`package.ps1` 会检查发布目录必须包含 EXE、应用 PRI、`App.xbf`、`MainWindow.xbf` 和 `Controls\HeatmapStrip.xbf`，缺少任一文件即终止打包。发布验证还应启动 NativeAOT EXE，并分别测量主窗口和托盘状态。
